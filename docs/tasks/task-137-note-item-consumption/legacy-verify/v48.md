## 1. Cash-item-use request builder

`CWvsContext::SendConsumeCashItemUseRequest` exists at **`0x70e495`**
(mangled `?SendConsumeCashItemUseRequest@CWvsContext@@QAEXJJJV?$ZXString@D@@@Z`, size 0x3976).
Signature = `void __thiscall(long slot, long itemId, long, ZXString<char>)`.

Prologue (before the type switch):
- `0x70e4f9` `push 3Eh` → `0x70e4fe` `COutPacket::COutPacket(long)` — opcode **0x3E**.
- `0x70e50c` `Encode2(arg_0)` — slot, int16.
- `0x70e517` `Encode4(arg_4)` — itemId, int32.
- `0x70e51f` `call get_consume_cash_item_type(itemId)` → type in eax.
- `0x70e527` `add eax,-12` / `0x70e52a` `cmp eax,0x23` / `0x70e52e` `ja default` / `0x70e53c` `jmp ds:jpt_70E53C[eax*4]` — 36-case switch over types 12..47 (index = type-12).

## 2. Type gate (classification 509)

`get_consume_cash_item_type` at **`0x47742e`** (`?get_consume_cash_item_type@@YAJJ@Z`):
- `0x477432` `call ZMap<long,ZRef<CItemInfo::LOTTERYITEM>,long>::GetAt(itemId)` — the item→cash-type mapping is a **ZMap loaded from item WZ (`LOTTERYITEM`/cash) data**, NOT a hard-coded `itemId/10000==509` switch (that hard-coded form is the v83 shape).
- Then range-filter: passes types 12–28, 30, 31, 34, 36–42, 43, 47; everything else → 0 (→ switch default → no packet).

Consequence: there is **no static `case 509`** to cite in v48 — the type value for 5090000 comes from client Item WZ. The *memo-send arm* is **type 19** (jump-table index 7 → `0x70ecb3`), which is inside the passed range. v83 maps 509→21 and type 21 = memo; in v48 the same semantic arm sits at type **19** (the enum shifted between v48 and v83). Item→type value for 5090000 is unverifiable from the binary alone (WZ-dependent), but the memo compose-send arm itself is unambiguous (see §3).

Jump table `jpt_70E53C` @ `0x711e0b` (read verbatim), index→arm:
idx0/1(t12/13)`0x70e543`, idx2(t14)`0x70eda0`, idx3(t15)`0x70ef55`, idx4(t16)`0x70f287`, idx5(t17)`0x70f53c`, idx6(t18)`0x70f6f7`, **idx7(t19)`0x70ecb3` = MEMO**, idx8(t20)`0x70ff9c`, idx9(t21)`0x70f9e0` (pet/slot arm — NOT memo), … idx22(t34)`0x711d60` (shared send-tail).

## 3. Note arm (compose: recipient + message)

Type-19 arm @ **`0x70ecb3`**:
- Allocates + constructs a `CDialog` via `sub_5EF8B6` (`0x5ef8b6`), UI resource id 2350, vtable `off_7A1544`.
- `sub_4A0A2B` (DoModal wrapper) → on OK, `sub_5EFEC0` (`0x5efec0`) reads **two `CCtrlEdit::GetText`** values into `arg_0`,`arg_4`.
- `0x70ed48` `EncodeStr(arg_0)` = recipient (toName); `0x70ed61` `EncodeStr(arg_4)` = message.
- `0x70ed9b` `jmp loc_711D60` → shared send epilogue.

Dialog OnCreate `sub_5EF9EC` (`0x5ef9ec`, vtable slot [3]) proves it is a **note/memo compose**:
- CCtrlEdit control **1000** (`this+144`), created with **max length 12** (`v24=12` @ `0x5efbe4`) — a MapleStory character name (recipient).
- CCtrlEdit control **1001** (`this+152`), created with **max length 100** (`v24=100` @ `0x5efc4d`) — the message body.
- `sub_5EFEC0` reads control 1000 → `arg_0` (recipient) first, control 1001 → `arg_4` (message) second.

`get_update_time` as a named function does **not exist** in v48 (`func_query` empty); v83 has it at `0x987257` and its `SendConsumeCashItemUseRequest` (`0xa0a63f`) calls it. In v48 the trailing timestamp is instead read inline from a cached context field (see §4), so the wire field survives even though the helper name is gone.

## 4. updateTime — TRAILING

Shared send epilogue `loc_711D60` @ **`0x711d60`** (also type-34's own arm):
- `0x711d69` `call sub_4A2518(ctx,500,0)` — CanSendExclRequest / 500 ms rate-guard; on fail → Notice(str 288), no send.
- `0x711d96` `call SetExclRequestSent` — **this symbol is mis-named; it is a getter**: body @ `0x6c1bcf` = `mov eax, ds:dword_80CA08; mov eax,[eax+18h]; retn` → returns `*(CWvsContext+0x18)` (cached update-time value).
- `0x711d9f` `Encode4(eax)` — trailing 4-byte updateTime.
- `0x711da8` `call sub_711EC9` = `CClientSocket::SendPacket` (`sub_711EC9` @ `0x711ec9` → `0x464cd1`).

So updateTime (`ctx+0x18`) is encoded **after** toName/message, immediately **before** SendPacket → **TRAILING**, identical position to v83.

`0x70e4f9` `push 3Eh` immediately precedes `0x70e4fe` `COutPacket::COutPacket(long)` — the COutPacket ctor immediate is **0x3E**. Matches seed `CharacterCashItemUseHandle` @ 0x3E.

## 7. MEMO_RESULT clientbound — `CWvsContext::OnMemoResult` @ `0x71d8e2`

`mode = Decode1() - 2` then dispatch (handler located by symbol; the clientbound opcode number was not separately traced through the OnPacket dispatcher — **unverified opcode**):
- raw **2** (`v3==0`) @ `0x71d9a9`: LOAD/receive — `Decode1()` count, loops `sub_4BFE98`+`sub_49CCDB` per memo; may spawn `CUIFadeYesNo::CreateNewMemo` "read note?" fade prompt (`0x71da0e`).
- raw **3** (`v5==0`) @ `0x71d990`: single `Notice(str 2425)`.
- raw **4** (`v5==1`) @ `0x71d913`: **SEND result** — clears excl flag (`off_80C8A0[2079]=0`, `SetExclRequestSent`), then `error = Decode1()`:
  - error **0** → `Notice(str 2372)` (`0x71d97d`)
  - error **1** → `Notice(str 2373)` (`0x71d956`)
  - error **2** → `Notice(str 2374)` (`0x71d945`)
  - else → return
- raw 0/1 → fall through, no-op (`0x71d90d`).

SEND error arms are 0/1/2, each a localized Notice string (IDs 2372/2373/2374 — not statically resolvable to text). There is **no distinct client-side "no note item" arm**; "no note item" is a server-side rejection surfaced as one of these Notice strings.

## 8. NOTE_ACTION (opcode 0x65) writers

Enumerated all opcode-101/102 COutPacket construction sites (scoped `insn_query` over the code; the note-dialog region 0x530000–0x540000 has exactly one 0x65 site). String-pool loads of 101/102 (e.g. `sub_4BBC68`) were excluded — those are `sub_5D75AF` string-resource lookups, not packets.

**Only genuine 0x65 client writer: `CMemoListDlg::SetRet` @ `0x534dc4`** (received-note management — reply/keep/discard):
- `0x534e45` `COutPacket(v27, 101)` → opcode **0x65**.
- `0x534e52` `Encode1(1)` → **mode byte = 1**.
- `0x534e6c` `Encode1(totalReceivedCount)`.
- `0x534e9a` `Encode1(count of notes with flag==2)`.
- `0x534ea5` `Encode1(emptySlotCount)` (`GetEmptySlotCount(4)`).
- per received-note loop:
  - flag==2 (reward/item note, accept): `Encode4(sn @+8)` `0x534f60`, `Encode1(flag @+24)` `0x534f75`, `Encode4(rewardValue)` `0x534f80`.
  - else: `Encode4(sn @+8)` `0x534ed7`, `Encode1(flag @+24)` `0x534eec`.
- `0x534fd8` `SendPacket`.
- second loop, flag==1 notes: `sub_57B7C7(102,0)` re-inits packet as **opcode 0x66 (102)** (`0x535001`), `Encode1(flag)` (`0x535016`), `SendPacket` (`0x535025`).

Discard/receive body shape (mode 1):
`[0x65][mode=1 u8][totalCount u8][flag2Count u8][emptySlots u8]{ per note: sn i32, flag u8 [, reward i32 if flag==2] }`.
This is the NOTE_ACTION "receive/discard" family. No mode-0 (compose SEND) writer exists at opcode 0x65 — the compose-SEND is the cash-item path (§1–§5).

## Bottom line for Atlas

v48 **DOES** emit a player-initiated note send via the **USE_CASH_ITEM (0x3E)** path. Atlas must **implement + gate a cash-item note-send arm for v48** — do **not** mark n-a. Wire = `[0x3E][slot i16][itemId i32][toName str][message str][updateTime i32]` (updateTime trailing), i.e. structurally the same as v83 (the cash-type enum differs: v48 type 19 vs v83 type 21, but that is client-internal and does not affect the serverbound wire). The separate NOTE_ACTION (0x65) path is receive/discard management only (mode 1); its discard body is documented in §8 (relevant to the unverified `NoteOperationDiscard` codec cell).
