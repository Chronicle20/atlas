# task-137 FR-1 legacy verify — GMS v61 (note-item consumption via USE_CASH_ITEM)

**Binary:** `GMS_v61.1_U_DEVM.exe.i64` (IDA session `965202bf`, confirmed via `idb_list`).
**Serverbound opcodes (Atlas seed):** `CharacterCashItemUseHandle` = 0x49, `NoteOperationHandle` = 0x77.

## TOP LINE
- **CASH-ITEM NOTE SEND ARM: PRESENT in v61.**
- **updateTime: TRAILING** (Encode4 after both strings; GMS < v87 convention, same as v83).
- **509 type-gate value: 20** (v61) — NOTE: differs from v83, where 509 → 21.

## Wire shape — USE_CASH_ITEM note send (opcode 0x49, item 5090000 / class 509)

| Order | Field | Encoder | Addr | Notes |
|------:|-------|---------|------|-------|
| — | opcode 0x49 | `COutPacket::COutPacket(0x49)` | 0x832abe (`push 49h`) → ctor 0x832ac3 | header |
| 1 | slot | Encode2 (int16) | 0x832ad1 | common header, arg_0 |
| 2 | itemId | Encode4 (int32) | 0x832adc | common header, String2 = itemId |
| 3 | toName | EncodeStr | 0x8335eb | note arm (case type 20) |
| 4 | message | EncodeStr | 0x833604 | note arm |
| 5 | updateTime | Encode4 (int32) | 0x83672e | shared send tail, **TRAILING** = get_update_time() |

Then `CClientSocket::SendPacket` (sub_83683D → 0x474125) at 0x836737; real `SetExclRequestSent(1)` = sub_83684D at 0x836741.

This matches the known-good v83 shape exactly (slot i16, itemId i32, EncodeStr toName, EncodeStr message, trailing Encode4 updateTime).

## Deliverable 1 — Cash-item-use request builder exists
`CWvsContext::SendConsumeCashItemUseRequest(long,long,long,ZXString<char>)` @ **0x832a5d** (mangled `?SendConsumeCashItemUseRequest@CWvsContext@@QAEXJJJV?$ZXString@D@@@Z`). ## Deliverable 2 — Type gate for classification 509
The itemId→type map is a real switch on `itemId/10000`, in the function @ **0x48a522** (symbol mis-demangled as `ZMap<...>::GetAt`; it is `get_cashslot_item_type`). Wrapper/validator `sub_48A4D6` @ 0x48a4d6 passes valid types 12..52 through.
- **`case 509: return 20;`** @ **0x48a5eb** → item 5090000 maps to consume-cash type **20**.
- (For contrast in the same table: 504→21, 508→17, 510→19, 520→18. v61 numbering is shifted vs v83; 509 is 20 here, not 21.)

## Deliverable 3 — Note name/message modal + two EncodeStr
Note arm = switch case **type 20** → **loc_833556** (jump-table index 8; IDA labels it "case 20"). It:
- Retrieves recipient + message via `sub_695453(&toName,&message)` @ 0x8335d2 (out-params reuse arg_0 / String2 stack slots after the header already encoded slot+itemId).
- **EncodeStr(toName)** @ **0x8335eb**, **EncodeStr(message)** @ **0x833604** (two consecutive strings; no other field between them).
- Recipient-then-message ordering asserted by structural parallel to v83 and to the gift writer (name first, message second).
CONFIRMED: name + message pair is present.

## Deliverable 4 — updateTime position: TRAILING
After encoding the two strings the arm `jmp loc_833519` (0x83363e) → gate `sub_4BDB9F(0x1F4)` → send tail **loc_836725**. There:
- `call 0x7cef6d` @ **0x836725** — **MISLABELED as `SetExclRequestSent`; actually `get_update_time()`** (`mov eax,g_CWvsApp; mov eax,[eax+18h]; retn`).
- `push eax` → **Encode4** @ **0x83672e** → trailing 4-byte updateTime.
So updateTime is encoded LAST, after both strings — TRAILING. (My initial "get_update_time not a callee" read was a false negative caused by this bad symbol; verified by disassembling 0x7cef6d.)

## Deliverable 7 — CWvsContext::OnMemoResult (clientbound MEMO_RESULT) @ 0x8468be
First byte = mode via `Decode1` @ 0x8468da. Reconstructed dispatch (`mode - 2` then `-1`):
- **mode 2** (else branch @ 0x846985): MEMO **LOAD** — `ZList<GW_Memo>::RemoveAll`, `Decode1` = count, loop count× (`sub_4E0F3D` add + `sub_4B59FD` decode one memo), then optional `CUIFadeYesNo::CreateNewMemo` fade window.
- **mode 3** (@ 0x84696c): Notice string id 2652 (single notice), then `CUtilDlg::Notice`.
- **mode 4 = SEND_ERROR** (@ 0x846913): reads a second `Decode1` sub-code:
  - code **0** → Notice string 2598 (@ 0x846959)
  - code **1** → Notice string 2599 (@ 0x846932)
  - code **2** → Notice string 2600 (@ 0x84691b/0x846921)
  - other → return (ignored)
- modes 0, 1, ≥5 → `return` (unhandled).

Notes: SEND_ERROR is **mode 4** in v61 (not mode 5 as in the v83-era reference). Sub-codes are 0/1/2 as expected. **No "no note item" arm exists** — the send-error codes are receiver-side only (as anticipated).

## Deliverable 8 — NOTE_ACTION (opcode 0x77 / 119) writers
Enumerated every COutPacket(119) construction site (full-binary `push 119` scan → only two feed the COutPacket ctor):

1. **`CMemoListDlg::SetRet` @ 0x5ad50c — mode 1 (DISCARD / receive-all).**
   - Guard: only when `a2 == 1 || a2 == 2`, and after `CUtilDlg::YesNo` (string 2586) returns 6.
   - `COutPacket(119)` @ **0x5ad58d**; `Encode1(1)` @ **0x5ad59a** = mode 1.
   - **Discard body shape:**
     - `Encode1(mode=1)` @ 0x5ad59a
     - `Encode1(totalCount)` @ 0x5ad5b4 — total memos (array length `this[45]`)
     - `Encode1(giftCount)` @ 0x5ad5e2 — count of memos whose flag `*(entry+24)==2`
     - `Encode1(emptySlotCount)` @ 0x5ad5ed — `GetEmptySlotCount(4)`
     - per-memo loop:
       - if flag==2 (gift/parcel memo) AND empty slots remain: `Encode4(memoSN=*(entry+8))` @ 0x5ad6a9, `Encode1(flag=*(entry+24))` @ 0x5ad6be, `Encode4(itemId)` @ 0x5ad6c9 (itemId = atoi of memo-string left of "_"); if no slots, set inventory-full flag and SKIP (client shows Notice 4173, entry not encoded)
       - else (normal memo): `Encode4(memoSN)` @ 0x5ad61f, `Encode1(flag)` @ 0x5ad634
     - `CClientSocket::SendPacket` @ 0x5ad721
   - This is more elaborate than a plain "mode,count,[SN…]" — it interleaves normal (SN+flag) and gift (SN+flag+itemId) records and self-filters gift entries by free inventory. Atlas's v61 NoteOperationDiscard codec (matrix ❌) must model this exact shape.

2. **`CCashShop::OnCashItemResLoadGiftDone` @ 0x461758 — mode 0 (gift SEND).**
   - `COutPacket(0x77)` @ **0x461899**; `Encode1(0)` @ **0x4618a6** = mode 0.
   - Body: mode0, `EncodeStr(toName)` @ 0x4618ca, `EncodeStr(message)` @ 0x4618e3, `Encode1(1)` @ 0x4618ed, `Encode4(giftId)` @ 0x4618f6, `EncodeBuffer(src,8)` @ 0x461909, then `SendPacket` @ 0x461918.

**No mode-2 "request note list" writer exists in v61.** (`OnMemoNotify_Receive` is absent; the note list arrives via clientbound OnMemoResult mode 2, and the gift list via OnCashItemResLoadGiftDone.) v61 emits only NOTE_ACTION modes **0** (gift send) and **1** (discard) — fewer writers than v83, as anticipated.
