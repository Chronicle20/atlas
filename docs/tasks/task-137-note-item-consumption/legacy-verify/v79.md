# task-137 FR-1 — GMS v79 cash-item note-send verification

Binary: `GMS_v79_1_DEVM.exe.i64` (IDA session `9a7d3642`, confirmed via `idb_list`).

- **updateTime: TRAILING** (encoded after the two strings, in the shared send tail — matches GMS < v87).

## Deliverable 1 — Type gate (itemId → cash-slot type)
- Classifier is `sub_47EC3E` (renamed **`get_cashslot_item_type`**) @ **0x47ec3e** — `switch (itemId / 10000)`.
- **`case 509: return 21;`** @ **0x47ed40**. Classification 509 → type **21** (matches v83).
- `is_select_npc_item` @ 0x47ebbd wraps it and passes 21 straight through (12 ≤ 21 ≤ 32, ≠ 34 → `return result`), so the value reaching the switch is 21.
- The switch in `SendConsumeCashItemUseRequest` applies bias `add eax, -12` (0x9563e4) then `jmp ds:jpt_9563F1[eax*4]` (0x9563f1). Disassembler annotates the type-21 target as `case 21` = **loc_9572F1**.

## Deliverable 2 — Note arm (type 21) in SendConsumeCashItemUseRequest
- Arm entry **loc_9572F1** @ **0x9572f1** (`push 9Ch; ...case 21`).
- Allocates the input dialog object (`Alloc(0x9C)` 0x9572fb + ctor `sub_74EC42` 0x95730d), seeds message from arg (`sub_95FC94` 0x957360), then executes the modal via `sub_4E1832` @ 0x95736f (returns 1 on confirm → falls to encode at loc_957389; otherwise cleans up and returns with no send).
- On confirm (0x957389): extracts recipient + message from the dialog (`sub_74F2AB` 0x95739e), then:
  - `EncodeStr(toName)` @ **0x9573b7**
  - `EncodeStr(message)` @ **0x9573d0**
  - then `jmp loc_9565FC` into the shared send tail.
- Confirmed: this arm opens a name/message input modal and encodes `EncodeStr(toName)` then `EncodeStr(message)`.

Note: the input modal here is `CUtilDlgEx` (the SetUtilDlgEx path visible in the neighbouring case-16 arm at 0x9574f2); the type-21 arm uses the same modal family (`sub_4E1832` exec). The two encoded strings are the load-bearing fact and are verified above.

## Deliverable 3 — updateTime position
- **TRAILING.** The encoded `updateTime` is written in the shared send tail **loc_95A545**, *after* both `EncodeStr` calls:
  - `SetExclRequestSent` @ 0x95a545
  - `Encode4(updateTime)` @ **0x95a54e** (eax = `get_update_time()` return from loc_9565FC @ 0x956605)
  - `SendPacket` @ 0x95a557
- The two `get_update_time(0x1F4, 0)` calls at 0x956381 (header) and 0x956605 (loc_9565FC) are rate-limit **guards** (`test eax,eax; jnz`), not the encoded value; the encoded value is the single trailing `Encode4` at 0x95a54e.
- Confirms the "GMS < v87 → trailing" hypothesis.

## Deliverable 7 — NOTE_ACTION (opcode 0x80) serverbound writers
Opcode 0x80 is unique to the note-action packet, so every `COutPacket(0x80)` ctor site is a note-action writer. Exhaustive check of `push 80h` sites (293 total) plus decompilation of all note-UI entry points yields **exactly 2 writers** — there is **no mode-0 writer**:

| writer | addr (COutPacket 0x80) | mode byte | body |
|--------|------------------------|-----------|------|
| `CMemoListDlg::SetRet` | ctor 0x619fb7 (`push 80h` 0x619fa6) | **1** (`Encode1(1)` @ 0x619fc4) | discard/receive — see below |
| `CWvsContext::OnMemoNotify_Receive` | ctor 0x96f316 (`push 80h` 0x96f30e) | **2** (`Encode1(2)` @ 0x96f324) | mode byte only, then `SendPacket` (request/ack) |

### `CMemoListDlg::SetRet` (mode 1) discard/receive body
Fires on the memo-list confirm (`a2 == 1 || a2 == 2`, but the encoded mode byte is hard-coded `1` either way). Header + variable per-entry loop:
1. `Encode1(1)` — mode = 1 @ 0x619fc4
2. `Encode1(totalMemoCount)` — ZArray element count of the memo list @ 0x619fde
3. `Encode1(giftMemoCount)` — count of entries whose flag(+24)==3 @ 0x61a00c
4. `Encode1(emptySlotCount)` — free ITEM (tab 4) inventory slots @ 0x61a017
5. per memo entry (loop over the list):
   - normal entry (flag ≠ 3): `Encode4(memoId +8)` @ 0x61a049, `Encode1(flag +24)` @ 0x61a05e
   - gift entry (flag == 3) **and** a free slot remains: `Encode4(memoId +8)` @ 0x61a0d3, `Encode1(flag +24)` @ 0x61a0e8, `Encode4(value)` @ 0x61a0f3 (value = `atoi` of the field before the `'_'` separator), then `--emptySlotCount`
   - gift entry with no free slot: sets an "inbox full" flag (`v33=1`), encodes nothing for that entry (later shows StringPool 4234 notice)
6. `SendPacket` @ 0x61a14d

### Mode 0 (gift SEND) — ABSENT
The task's expected mode-0 writer `CCashShop::OnCashItemResLoadGiftDone` @ 0x47252c is a **pure clientbound reader** (`Decode2` count @ 0x472548 + `DecodeBuffer(98*count)` @ 0x47256c); it constructs no COutPacket. Its internal `push 80h` @ 0x472654 is an alloc/size constant, not an opcode. No other `COutPacket(0x80)` site exists in v79 (spot-checked memo-adjacent clusters: 0x967ea0 = `UINT128::UINT128`, 0x9744ec = `ZAllocEx::Alloc(128)` in a name-change reader — neither is a packet). Player-initiated note SEND in v79 is done **exclusively via the cash item on opcode 0x4D**, not via a NOTE_ACTION mode-0 arm.
