# The v0.48 ↔ v0.62 boundary: GM/SuperGM ↔ Pirate/Brawler

Provisioned columns straddling this boundary: **gms 48, gms 61, gms 72**
(v0.62 Pirate release itself is not a provisioned column — the boundary is
observed via the WZ state at these three provisioned tuples).

All evidence below is WZ evidence drained from the live `atlas-data`
baseline (see `README.md` for tenant IDs / drain method). IDA `func_query`
was attempted per Step 3 and did not yield job/skill-constant symbol names
for these three IDBs (see `README.md`, "IDA evidence attempt"); one
structural IDA finding is cited at the end of this document as
corroborating (not identity) evidence.

**The reassignment happens between v48 and v61, not between v61 and v72.**
At v61 the wireId already carries Pirate/Brawler skill data (proven by the
skill names, still untranslated placeholders at this point), even though
the class is not yet playable (meymink v0.61: "Pre Pirate Quests"; v0.62:
"Pirate Class"). v61 is therefore the "WZ stub present, released=false"
case for job 500/510, exactly analogous to the later Aran/Dual Blade
pre-release stubs recorded in `divergences.csv`.

## job 900 / job 910 (GM/SuperGM's new home)

- **gms 48:** absent. The full job list totals 37 jobs, the highest job id
  is `510`; there is no `900` or `910` entry.
- **gms 61:** present, 44 jobs total. `900` = "Haste (Normal)" /
  "Super Dragon Roar" / "Teleport" (exactly job 500's old GM roster,
  moved). `910` = "Heal + Dispel" / "Hide" / "Resurrection" (job 510's old
  SuperGM roster, moved) **plus** three new skills not present in v48's
  job 510: "Super Dragon Roar", "Teleport", "Hyper Body" (`9101006-9101008`).
- **gms 72:** present, same roster as gms 61.

GM and SuperGM relocate from `500`/`510` to `900`/`910` in the same v48→v61
window that job `500`/`510` acquire their Pirate/Brawler WZ stub — a single
coordinated reassignment, not two independent events.

## Corroborating IDA evidence (structural, not identity)

`is_correct_job_for_skill_root` decompiles identically in gms_48
(`0bb5f11a`, addr `0x5c1737`) and gms_72 (`90e36cb0`, addr `0x6b682a`):

```c
BOOL __cdecl is_correct_job_for_skill_root(int a1, int a2)
{
  if ( !(a2 % 100) )
    return a1 / 100 == a2 / 100;
  return a2 / 10 == a1 / 10 && a1 % 10 >= a2 % 10;
}
```

The client's job-hierarchy matching logic (tier check via `/100`, sub-tier
check via `/10` and `%10`) is byte-for-byte unchanged across the boundary.
This corroborates that the 500/510→900/910 relocation is a pure WZ-data
reassignment — the engine's generic job-code algorithm did not need to
change to accommodate it. It does not itself identify what 500/510/900/910
*mean* at each version; that identification rests on the WZ evidence above.

`func_query name_regex` searches for GM/SuperGM/Pirate/Brawler/Hide-related
symbol names across all three IDBs returned no matches beyond
auto-generated `sub_XXXXXX` names (see `README.md` for the full list of
patterns tried). No `func_query` evidence contradicts the WZ findings above
— it simply did not independently corroborate them at the symbol-name
level, which is expected given these IDBs' known lower naming density.
