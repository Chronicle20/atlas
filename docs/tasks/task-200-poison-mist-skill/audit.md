## Post-Review Fix Wave Verification

All three human-authorized departures from the plan text are implemented coherently:

1. **`PlayerMistTickIntervalMs` raised 1000→3000ms** — `skill/handler/poisonmist/poisonmist.go:53`, `const PlayerMistTickIntervalMs int64 = 3000`, with a doc comment (lines 27-52) explaining this is the mist's *re-apply* cadence, distinct from the monster damage-tick cadence, and citing the rationale (commit `0c2f0646b`, "raise PlayerMistTickIntervalMs to 3000ms so poison DoT actually ticks"). The plan's own zero/short-lifetime rejection gate (`duration < PlayerMistTickIntervalMs`) automatically tracks the new constant — no stale hardcoded `1000` comparison found elsewhere.
2. **Separate `monsterDotTickIntervalMs = 1000` on APPLY_STATUS** — `tasks/mist_tick.go:85`, distinct constant from the mist's own `TickInterval()`; wired at `tasks/mist_tick.go:227` (`TickInterval: monsterDotTickIntervalMs`) inside `applyStatusCommandProvider`, i.e. NOT echoing `m.TickInterval().Milliseconds()`. Extensive doc comment (lines 57-79) explains the `P - T` eligible-damage-window math and explicitly documents the earlier failed fix attempt (setting `T == P`, window collapsing to 0) that this constant supersedes. `mist_tick_monster_test.go:234-239` pins `monsterDotTickIntervalMs < PlayerMistTickIntervalMs` behaviorally.
3. **Bounded per-call REST timeout + bounded per-tenant concurrency** — `tasks/mist_tick.go:35-55` (`MistRectRequestTimeout = 500ms`, `MistRectRequestRetries = 1`), wired into the `monstersInRect` seam at `tasks/mist_tick.go:277` via `requests.SetTimeout(...)`/`requests.SetRetries(...)` passed through `monster.NewProcessor(l, ctx).GetInMapRect(..., configurators...)`; `monster/processor.go:60` confirms `GetInMapRect` accepts and forwards `configurators ...requests.Configurator`. Concurrency bound: `mistTenantConcurrency = 4` (`tasks/mist_tick.go:86`), wired via a buffered channel semaphore in `processTenant` (`tasks/mist_tick.go:322-336`) gating goroutine fan-out per tenant. `TestMistTick_MonsterTarget_LookupFailureIsolatedPerMist` (existing from Task 8) continues to cover per-mist isolation under this concurrent path; commit `675003ff0` ("make mist-fan-out latency-isolation test deterministic") confirms the concurrency change was test-verified, not just added.

Nothing found broken by these three changes: `buff-duration-guard.sh` still passes (character-branch `duration` stays ms), the `ApplyStatusCommandBody` key set is unchanged, and all `atlas-maps`/`atlas-monsters` test suites pass with `-count=1`.
