## 1. Money and asset conservation

**Verdict: PASS**, with citations.

### Meso escrow compare-and-set (armed/committed/abandoned)

- `services/atlas-trades/atlas.com/trades/escrow/administrator.go:186-198` (`CommitMesoStake`) and `:204-215` (`AbandonMesoStake`) resolve a pending stake with a single `UPDATE ... WHERE pending_stake_id = ?` — the match and the clear happen in one statement, so two concurrent deliveries of the same (or a stale, superseded) terminal status cannot both observe "armed" and both commit. Only the delivery whose `UPDATE` actually matches a row (`RowsAffected > 0`) proceeds.
- `services/atlas-trades/atlas.com/trades/trade/processor.go:1289-1358` (`resolveMesoStake`) checks `matched` from that compare-and-set before touching the in-memory room, so a redelivered `MesoStageSucceeded`/`MesoStageFailed` is a no-op (`p.l.Debugf("... already resolved ...")`, line 1315) and cannot double-commit or double-refund.
- `services/atlas-trades/atlas.com/trades/trade/processor.go:1327-1328` and `refundOrphanedStake` (`:1361-1392`) refund the **delta** (`amount - row.Amount()`), not the absolute stake, when a room disappears mid-stake — so the teardown's own unwind (which refunds the already-committed `Amount`) and this delta refund cannot double-pay.
- `escrow/entity.go:116-134` documents `MesoEntity.Amount` as ABSOLUTE-not-delta, and `UpsertMeso` (`administrator.go:106-132`) REPLACEs rather than accumulates — matches `trade/processor.go:1203-1219` (`addMeso`), which reads the escrow row fresh (not the in-memory room) and computes `delta := int64(amount) - int64(escrowed)` before arming a stake.

### Item escrow rows

- `escrow/administrator.go:57-68` (`CreateItem`) uses `ON CONFLICT (id) DO NOTHING`, making a redelivered `ACCEPT_TO_TRADE` command idempotent on the row id (comment at `:59-62` states this explicitly and correctly — a second create would otherwise let the unwind return the item twice).
- `RemoveItem` (`:94-104`) is a HARD delete (`db.Unscoped()...Delete`), documented as the correct inverse of a spurious `AcceptToTrade` whose paired release later failed — a soft-deleted (restorable) row here would let a later unwind re-deliver an item already re-granted. `DeleteItem`/`RestoreItem` (`:70-92`) are soft-delete/un-delete, which is correct for the release↔restore pair since that item is still legitimately "in the system" and recoverable.
- Orphaned-stage return: `trade/processor.go:1057-1079` (`returnOrphanedStage`) is reached from `stageSucceeded` when `findStagedItem` finds no dialog slot for the escrow id (room torn down while the stage was in flight) — it issues a one-item `TradeUnwind` to return it. This is the only path that can return an orphaned row, and it is reached exactly once per `StageSucceeded` delivery.

### Orchestrator-side settlement/unwind expansion

- `saga/processor.go:1559-1634` (`expandTradeSettlement`): meso is credit-only — the giver was already debited at stage time (escrow), so the expander emits only `AwardMesos` credits to the *other* side (`:1613-1631`), never a matching debit. The doc comment at `:1551-1554` explicitly calls out that emitting the old negative leg here would double-charge the giver, and the code matches that description.
- `saga/processor.go:1645-1707` (`expandTradeUnwind`): releases precede accepts precede meso refunds (comment `:1547-1550`, `:1658-1660`), so a mid-expansion failure never creates before it has released.
- `saga/compensator.go:1912-1974` (`DispatchTradeTransactionRollbacks`) and `:2451-2515` (`DispatchTradeStagingRollbacks`) both reverse-walk **newest-first** and gate every inverse behind `claimTradeRollback` → `claimLateCompensation` (`:1976-2001`), a per-step optimistic-version marker shared with the late-success absorption path (`:2273-2314`). This closes the double-compensate window between a synchronous compensation and a late-arriving success event for the same step — verified idempotency, not just claimed.
- `AwardMesos` inverse is `-Amount` (`:1929`, `:2279`); `AcceptToCharacter` inverse is `RequestDestroyItem` (template+quantity, `:1949`); `ReleaseFromTrade` inverse is `RestoreTradeEscrow` (un-soft-delete, `:1965`) rather than a re-grant directly to the character — the comment at `:1896-1902` gives the correct reason (a direct re-grant here could race an accept that already delivered the same item to the counterparty; restoring to escrow and letting the subsequent teardown/unwind hand it back cannot).

**No path found that can debit without recording, refund twice, or strand an item.** The ledger (`ledger/administrator.go:96-149`) and settlement record (`settlement/administrator.go:72-134`) both rely on unique-index / rows-affected arbitration for the same reason (see §3 below).

## 2. Transaction scoping (`ProcessorImpl.emit`)

**Verdict: PASS**, with one clarifying note.

- `trade/processor.go:392-399` (`emit`): opens one transaction via `database.ExecuteTransaction(p.db.WithContext(p.ctx), ...)`, then `txp := p.withTx(tx)` and calls `f(txp, mb)` — every command handler (`createRoom`, `putItem`, `addMeso`, `confirm`, `settle`, `completeSettlement`, etc.) is invoked with the **shadowed, tx-scoped** `p` parameter, not the outer receiver.
- `trade/processor.go:404-409` (`withTx`): rebinds both `cp.db = tx` **and** `cp.esc = p.esc.withTx(tx)` — the escrow reader is explicitly re-pointed at the transaction, with a doc comment (`escrowStore.withTx`, `:153-163`) explaining that leaving it on the root handle is a deterministic deadlock at pool size 1 (a second pooled connection the transaction doesn't hold and can't release), not merely inefficiency. Verified this rebinding actually happens (not just documented) at `:406-407`.
- Every DB-touching helper called from inside an `emit` closure that I traced passes `p.db` (the shadowed, tx-scoped field) rather than a captured outer reference:
  - `escrow.NewProcessor(p.l, p.ctx, p.db).ArmMesoStake(...)` — `trade/processor.go:1231` (inside `addMeso`, itself inside `emit`).
  - `escrow.NewProcessor(p.l, p.ctx, p.db)` — `trade/processor.go:1290` (inside `resolveMesoStake`, inside `emit`).
  - `settlement.NewProcessor(p.l, p.ctx, p.db).Submit(...)` — `trade/settlement.go:490` (inside `settle`, inside `emit`).
  - `settlement.NewProcessor(p.l, p.ctx, p.db)` / `ledger.NewProcessor(p.l, p.ctx, p.db).Record(...)` — `trade/settlement.go:927,939` (inside `completeSettlement`, inside `emit`).
  - `ledger.create` (`ledger/administrator.go:96-149`) and `settlement.create` (`settlement/administrator.go:72-90`) both use `database.ExecuteTransaction`, which **joins** the caller's transaction (savepoint) when one is already open on the handle — so the ledger write and settlement record genuinely land in the same outbox transaction as the saga command and status event, not a nested/separate one.
- The one path that deliberately does **not** use the tx handle is documented and correct rather than a bug: `trade/settlement.go:150-159` (`detached()`) and `:176-197` (`Confirm`) arm the attestation deadline **outside** `emit`, against the root `p.db`/root context — because the deadline outlives both the transaction and the command's context, and the registry swap to `AWAITING_ATTESTATION` is in-memory and therefore not rolled back with the transaction regardless (comment at `:183-195` traces the failure mode this avoids: an unarmed wedged room). This is the single call site where `p.db` legitimately means the root handle, and it is explicitly commented as such (`:154`, "which is why Confirm arms from OUTSIDE emit, where p.db is still the root handle").
- `escrow/processor.go` itself is not transaction-participating for the "not saga step" methods (`UpsertMeso`, `DeleteMeso`, `ArmMesoStake`, `CommitMesoStake`, `AbandonMesoStake`, `MesoStakeById` — `:109-131`) — they write through whatever `p.db` was passed to `escrow.NewProcessor`, which in every call site traced above is the tx-scoped handle from the caller's `emit`. The saga-step methods (`Accept`, `Release`, `Restore`, `Remove`, `:65-107`) additionally wrap their own `message.Emit`, but are only invoked from the custody consumer (`services/atlas-trades/atlas.com/trades/kafka/consumer/custody`, not in this diff's changed-file list) rather than from inside `trade.ProcessorImpl.emit` — no double-transaction nesting found there.

No read or write found inside an `emit` closure that used the root `p.db`/`p.esc` instead of the tx-scoped copy.

## 3. Idempotency under Kafka redelivery

**Verdict: PASS.**

- **Settlement terminal status** (`SettlementSucceeded`/`SettlementFailed` → `completeSettlement`, `trade/settlement.go:891-983`): `sp.GetByTransactionId` returns `gorm.ErrRecordNotFound` for an already-resolved settlement and the handler treats that as "already resolved, ignoring" (`:930-933`) rather than an error. The **arbiter** is `sp.Resolve` (`settlement/administrator.go:101-134`, a delete keyed by `(tenant_id, transaction_id)` whose `RowsAffected` decides the winner) — `completeSettlement` only proceeds to remove the room and emit the client-visible event if `won` (`trade/settlement.go:946-953`). Two concurrent deliveries can both reach `ledger.Record` before either deletes the record, but `ledger.create` is itself idempotent per `(tenant_id, transaction_id)` via a unique index + read-back (`ledger/administrator.go:96-149`, `ErrDuplicateTransaction` handling at `:131-149`), so no double-credit results even from that race.
- **Item stage terminal status** (`StageSucceeded`/`StageFailed`): `stageSucceeded` (`trade/processor.go:967-998`) checks `!i.Pending()` (`:977-982`) and treats a re-delivery against an already-confirmed item as a debug-level no-op ("Ignoring the redelivery"). `stageFailed` (`:1011-1044`) has the same `!i.Pending()` guard (`:1016-1022`).
- **Meso stake terminal status**: covered in §1 — the durable compare-and-set on `pending_stake_id` is the guard, independent of the in-memory room.
- **Saga-orchestrator reverse-walk**: `claimLateCompensation`/`claimTradeRollback` (`compensator.go:1976-2001`) is the single idempotency gate shared by both the synchronous compensation path and the late-terminal-event absorption path (`:2273-2314`) — confirmed by reading both call sites route through the same claim function.
- **Escrow row writes**: `CreateItem`'s `ON CONFLICT DO NOTHING` (escrow/administrator.go:63-67) and `DeleteItem`/`RemoveItem` treating "already gone" as success (comments at `:70-75`, `:94-99`, matching the actual `Where(...).Delete(...)` calls which do not check `RowsAffected` and return the (nil) `.Error` only) are consistent with at-least-once delivery.

No path found where a redelivered terminal status can double-apply an award, double-release an escrow row, or re-emit a client-visible event that already fired.

## 4. Saga-status routing (`kafka/consumer/saga/consumer.go`, atlas-trades) — **BLOCKING FINDING** (found outside the four named risk areas, in the adjacent atlas-channel consumer this saga status ultimately drives)

### 4a. The three-way ownership probe itself: PASS

`services/atlas-trades/atlas.com/trades/kafka/consumer/saga/consumer.go:77-145` routes `handleSagaCompleted`/`handleSagaFailed` by trying, in ascending cost order: `StageSucceeded`/`StageFailed` (owns an escrow row by id) → `MesoStageSucceeded`/`MesoStageFailed` (owns a pending meso row by stake id) → `SettlementSucceeded`/`SettlementFailed` (owns a durable settlement record, unconditional fallback).

- The three id spaces are disjoint by construction: `escrowId` is minted via `uuid.New()` in `putItem` (`trade/processor.go:912`), `stakeId` via `uuid.New()` in `addMeso` (`:1230`), `settlementId` via `uuid.New()` in `settle` (`trade/settlement.go:455`) — three independent UUIDv4 generations, not a shared counter or derived value, so no id-space collision is possible in the way the three-probe comment (`consumer.go:60-72`) claims.
- A fourth transaction-id space exists that none of the three probes own: `TradeUnwind` sagas, whose `TransactionId` is `uuid.New()` minted fresh at `trade/settlement.go:621` (`emitUnwind`), `:1005` (`unwindRecord`), and `trade/processor.go:1071,1382` (`returnOrphanedStage`, `refundOrphanedStake`). Traced this through: none of the three probes claim it (it names no escrow row, no pending stake, no settlement record), so it falls through to `p.SettlementFailed`/`p.SettlementSucceeded` → `completeSettlement` → `GetByTransactionId` returns `ErrRecordNotFound` → silent, correct no-op (`trade/settlement.go:930-933`). **No mis-claim** — confirmed this is inert rather than a false-positive settlement resolution.

### 4b. Confirmed blocking bug in the downstream consumer this routing feeds

The stage-succeeded path (`trade/processor.go:StageSucceeded` → `stageSucceeded` → `mb.Put(trademsg.EnvEventTopicStatus, itemStagedProvider(...))`, line 997) emits `ITEM_STAGED` **after** the `transfer_to_trade` saga has fully completed — i.e., after `release_from_character` has already removed the asset from the owner's compartment (`saga/processor.go:1477-1489`, step 1) **and** `accept_to_trade` has written the escrow row (step 2, `:1490-1532`). This is the entire point of escrow-at-staging (design doc, `docs/tasks/task-205-player-trade/design.md:562-570`): the item genuinely leaves the compartment at stage time, before `ITEM_STAGED` fires.

`services/atlas-channel/atlas.com/channel/kafka/consumer/trade/consumer.go:446-469` (`handleItemStagedEvent`) still resolves the packet's stat payload by calling `tradeStagedAssetResolver` (`:262-279`), which reads the staging character's **live** compartment via `compartment.NewProcessor(l, ctx).GetByType(uint32(stagerId), b.InventoryType)` and looks up the asset by id (`c.FindById(uint32(b.AssetId))`, `:267-269`). By the time `ITEM_STAGED` is delivered, that asset has already been removed from the compartment (it moved to atlas-trades' escrow table, which atlas-inventory has no knowledge of) — so `FindById` will not find it, `errAssetNotFound` (`:283`) is returned, and `handleItemStagedEvent` calls `abortOnDisplayFailure` (`:456-462`), which **cancels the entire trade** (`abortOnDisplayFailure` → `tradeCancelRequester` → `tradeproc.NewProcessor(l, ctx).Cancel(...)`, `:292-294,316-325`).

This means **every successful item stage under the new escrow model cancels its own trade**, because the very event announcing the successful stage is unable to render itself. This is not a hypothetical: it is the direct, mechanical consequence of (a) the item leaving the compartment strictly before `ITEM_STAGED` fires (new in this diff) and (b) `handleItemStagedEvent`/`tradeStagedAssetResolver` still assuming reserve-at-staging semantics (unchanged by this diff — confirmed via `git diff aec7e0fbe..a3279ee73 -- .../kafka/consumer/trade/consumer.go` and `.../kafka/message/trade/kafka.go`: neither the resolver body nor `ItemStagedEventBody`'s fields changed in this commit range).

Evidence this is a real, unexercised gap rather than a documentation nit:

- `ItemStagedEventBody` (`services/atlas-channel/atlas.com/channel/kafka/message/trade/kafka.go:161-172`, unchanged in this diff) still carries only `Position, TradeSlot, InventoryType, SourceSlot, AssetId, TemplateId, Quantity` — no stat snapshot (`Strength`, `Dexterity`, `Flags`, `Owner`, etc.) — despite `settlement.go`'s `escrowItemPayload` (trade/settlement.go:564-594) and the orchestrator's `AcceptToTradePayload` (`saga/processor.go:1490-1532`) proving the stat snapshot is available at the point `ITEM_STAGED` is emitted (it is on the escrow row). Nothing threads that snapshot onto the wire event.
- `tradeStagedAssetResolver`'s own doc comment (`consumer.go:256-261`) still says "**Design §5 chose the RESERVE model over escrow-at-staging**, so a staged asset is still in the stager's own compartment and is read from there" — this is now factually false for the shipped code; it was not updated when the reserve→escrow amendment landed.
- The unit tests that exercise `handleItemStagedEvent` (`consumer_test.go:235-240,822-827`) both **stub `tradeStagedAssetResolver` directly** (`orig := tradeStagedAssetResolver; tradeStagedAssetResolver = func(...) {...}`), bypassing the real REST call entirely — this is precisely why `go test ./...` passes while the real code path is broken. `TestStagedItemDisplayFailureCancelsTheTrade` (`consumer_test.go:873`) proves the code path exists and is deliberate (a resolver error is *designed* to cancel the trade for a genuine display failure) — it just never anticipated the resolver failing on every call once the item is legitimately gone from the compartment by design.
- Confirmed via `git log`/`git diff` that `expandTransferToTrade`'s ordering (release before accept, `saga/processor.go:1477-1532`) and the "announce only when the staging saga completes" amendment (design.md:568-570, "when the STAGING SAGA COMPLETES, not when the custody command is handled") are the changes that create this timing; before this migration (reserve-at-staging), the asset legitimately remained in the compartment (only reserved, not removed) at `ITEM_STAGED` time, so the same resolver worked.

**Severity: Important/Blocking.** This is a structural break of the core trading flow (any item-carrying trade), not an edge case — meso-only trades would be unaffected, but the primary use case (trading items) fails on every attempt. Recommend before merge: either (a) extend `ItemStagedEventBody` with the item stat snapshot (mirroring `TradeEscrowItem`/`AcceptToTradePayload`) and switch `handleItemStagedEvent` to build the packet from the event body instead of a live compartment read, or (b) add a REST endpoint on atlas-trades' `escrow` package exposing the row by id and switch the resolver to call that instead of `atlas-inventory`.

## Summary

### Blocking (must fix)
- **[atlas-channel] `handleItemStagedEvent`/`tradeStagedAssetResolver`** (`services/atlas-channel/atlas.com/channel/kafka/consumer/trade/consumer.go:256-279,446-469`) resolve the staged asset from the stager's **live** atlas-inventory compartment, which no longer contains the item once escrow-at-staging removes it before `ITEM_STAGED` fires (`saga/processor.go:1477-1532`, `trade/settlement.go`/design.md:568-570). ## 1. Money and asset conservation — **FAIL** (new blocking defect)

### 1a. Scenario (a)/(c): meso stake in flight at teardown, later resolved — over-refund

Trace, with the exact state at each step:

1. A participant has an already-committed escrow meso total `X > 0` for the room (e.g. from an earlier `AddMeso`). They call `AddMeso` again with a new absolute total; `addMeso` computes `delta := amount - escrowed` (`services/atlas-trades/atlas.com/trades/trade/processor.go:1281`) and dispatches an `award_mesos` saga for only that **delta**, while durably arming the row via `ArmMesoStake(roomId, characterId, stakeId, uint32(amount))` (`processor.go:1298`) — `amount` here is the client's new **absolute** target `Y`, not the delta (confirmed: `ArmMesoStake`'s signature takes `amount uint32` and stores it verbatim as `PendingAmount`, `escrow/administrator.go:162-188`). Row state after arming: `Amount=X`, `PendingStakeId=stakeId`, `PendingAmount=Y`.
2. Before that saga's terminal status is delivered, the room is torn down (`teardownRoom`, `settlement.go:1337-1348`, reachable from EXIT/CRC-mismatch/logout/map-change/disconnect — no code path checks for an in-flight stake before tearing down; confirmed no caller of `teardownRoom` or `p.claimRoom` guards on `PendingStakeId`, `grep -n "PendingStakeId\|WithPendingMeso" trade/*.go` shows no such check outside `model.go`/`processor.go:1312`). `claimRoom` removes the room from the in-memory registry immediately (`settlement.go:1371-1378`, `p.reg.RemoveIf`), so **no restart is required** for the room to be "gone" from this point forward.
3. `teardownRoom` calls `emitUnwind` (`settlement.go:585-623`), which reads `p.esc.MesosByRoom(room.Id())` (`:590`) — this returns the row with `Amount()=X` (the committed value; the pending stake has not yet resolved so `Amount` is still `X`). Since `X>0`, the row is included in `payload.Mesos` with `Amount: X` (`:609-615`), and `p.clearRefundedMesos(room.Id(), payload.Mesos)` (`:619`) is called **before** submitting the unwind. `clearRefundedMesos` (`:1226-1234`) calls `ep.UpsertMeso(roomId, m.CharacterId, 0)`. `UpsertMeso`'s `ON CONFLICT DO UPDATE` clause only assigns `amount` and `updated_at` (`escrow/administrator.go:143-146`) — it does **not** touch `pending_stake_id`/`pending_amount`. Row state after teardown: `Amount=0`, `PendingStakeId=stakeId` (**still armed**), `PendingAmount=Y` (unchanged). The unwind saga refunds `X` to the player — correctly, since `X` was genuinely already escrowed.
4. The still-in-flight `award_mesos` saga eventually completes (or its terminal status is merely delayed/redelivered — no restart needed) and `MesoStageSucceeded(txId, stakeId)` is delivered to `resolveMesoStake` (`processor.go:1356-1426`). `row, found, err := ep.MesoStakeById(stakeId)` (`:1358`) reads the **current** row: `Amount=0` (from step 3), `PendingStakeId=stakeId`, `PendingAmount=Y`. `amount := row.PendingAmount()` = `Y` (`:1367`). `CommitMesoStake` matches on `pending_stake_id = stakeId` (still armed, unaffected by step 3's zeroing) and commits `Amount=Y` (`escrow/administrator.go:202-214`). `p.reg.Get(p.t, row.RoomId())` finds nothing (room removed in step 2) → `refundOrphanedStake(mb, row, amount)` is called (`processor.go:1394-1395`) with **`row` being the pre-commit snapshot read at `:1358`**, i.e. `row.Amount()==0`.
5. `refundOrphanedStake` (`:1434-1459`) computes `delta := int64(amount) - int64(row.Amount())` = `Y - 0 = Y` (`:1435`) and refunds the **full** `Y` via a fresh `TradeUnwind` (`:1449-1458`).

Net result: the player is refunded `X` (step 3, correct — that was genuinely already escrowed and returned) **plus** `Y` (step 5) — but the only real debit ever taken from the player's live wallet by the `award_mesos` saga was `delta = Y - X` (`processor.go:1281`, `1329`: `Amount: int32(-delta)`). Net player gain = `X + Y - (Y - X) = 2X` mesos minted from nothing whenever `X > 0` — i.e. whenever the player had already committed a nonzero stake before retyping the trade-meso box a second time and the room died while the second stake was in flight. This is not an edge case gated behind a crash: it requires only an ordinary teardown (EXIT, CRC mismatch, disconnect, map/channel change) racing an in-flight `AddMeso` saga, both of which are routine trade-lifecycle events.

`refundOrphanedStake`'s own doc comment (`processor.go:1428-1433`) states the correct intent — "The delta is what has to be refunded, not the absolute stake: the committed part was already returned by the teardown's own unwind, and refunding the total on top of it would mint meso" — but the delta it actually computes is against `row.Amount()`, and that field is exactly the one `clearRefundedMesos` zeroes as part of "the teardown's own unwind." The function is comparing against a value that its own sibling function (`clearRefundedMesos`) already destroyed. The bug is a genuine interaction between two of the fix's own new pieces (`clearRefundedMesos`, added in `b8c0db44c`, and the pre-existing `refundOrphanedStake`'s delta math), not a pre-existing defect: `clearRefundedMesos` and its call sites (`emitUnwind:619`, `unwindStranded:1275`) are new in this diff (`git diff a3279ee73..HEAD -- .../settlement.go` shows `clearRefundedMesos` and both call sites as additions).

**Same defect reachable at boot** (scenario (a) as literally asked): if the teardown in step 2/3 above happens, the service crashes/restarts before the stake resolves, `ReconcileEscrow` (`settlement.go:1146-1212`) skips the row entirely because `if m.Amount() == 0 { continue }` (`:1189-1191`) — the row is correctly *not* re-swept (it was already refunded). But the dangling armed stake (`PendingStakeId=stakeId`, `PendingAmount=Y`) is never cleaned up by boot recovery at all — it just sits until its terminal status is eventually delivered (possibly after the restart, e.g. a redelivered Kafka message), at which point the exact over-refund above still fires. Boot recovery closes the "item/meso genuinely lost" gap (Finding B) but does not close this over-refund gap; if anything it makes the stranded-stake window longer-lived (the row survives indefinitely with no ticker or boot pass ever touching `PendingStakeId`).

**Not caught by any test.** `TestUnwindZeroesARefundedMesoRowAndKeepsItsPendingStake` (`services/atlas-trades/atlas.com/trades/trade/settlement_reconcile_test.go:500-535`) seeds exactly this state (`escrow.ArmMesoStake(db, tm)(roomId, 200, stakeId, 900)` with a committed `5000`, `:509`) and asserts the row is zeroed with the pending stake preserved (`:522-534`) — but the test stops there. It never drives the stake to resolution (never calls `resolveMesoStake`/`MesoStageSucceeded` against the now-zeroed row), so it cannot observe the double-refund the zeroing sets up. No other test in the diff (`grep -rn "refundOrphanedStake" services/atlas-trades/atlas.com/trades/` matches only its own definition and its one call site, `processor.go:1086,1395`) exercises `refundOrphanedStake` at all — it has zero direct or indirect test coverage. This is exactly the "seam not tested" pattern the prior audit flagged for Finding D: the test proves the intermediate state described in the commit message's own reasoning, without proving the reasoning's conclusion (no double refund) actually holds once the next step in the sequence runs.

**Severity: Blocking.** Meso duplication on a routine, no-restart-required race, in code this fix pass itself introduced (`clearRefundedMesos`).

**Recommendation:** `clearRefundedMesos` (or `refundOrphanedStake`) needs to account for the amount already zeroed. The defect in 1a is not a double-delivery bug — it fires on a single, correct delivery of the stake's terminal status, given the row state left behind by a single teardown.

## 2. Meso row zeroed vs. deleted — mixed

- **Cannot be double-refunded via the sweep path itself: PASS.** `TestASecondSweepOverARefundedRoomSubmitsNothing` (`settlement_reconcile_test.go:540-558`) and the `if m.Amount() == 0 { continue }` guards in both `emitUnwind` (`settlement.go:606-608`) and `ReconcileEscrow` (`:1189-1191`) correctly prevent a zeroed row from being swept again by the boot pass or a second teardown.
- **An in-flight stake resolves against a zeroed row without erroring: PASS, but produces wrong output — FAIL on correctness.** `MesoStakeById` and `CommitMesoStake` operate on `pending_stake_id` independent of `Amount`, so resolution against a zeroed row does not error or panic (confirmed, §1a trace) — but as shown in §1a, "resolves without erroring" is not "resolves correctly": the zeroing destroys the information `refundOrphanedStake` needs to compute a correct delta.
- **Zeroed rows cannot accumulate unboundedly: PASS, with a caveat.** Growth is bounded by room cardinality (`uniqueIndex:idx_trade_escrow_mesos_room_owner` on `(tenant_id, room_id, owner_id)`, `escrow/entity.go:157,162-163`, so at most one row per room+owner ever exists — a zeroed row is reused, not duplicated, by any later `UpsertMeso`/`ArmMesoStake` against the same room+owner). No cleanup/deletion of zeroed rows exists, but since the key is bounded by (room, owner) and rooms are not reused across trades (`uuid.New()` per room, confirmed at the room-creation call site), the table grows with total trade count, same as `trade_escrow_items` after a hard-delete-free release — this is a storage-growth characteristic, not a correctness defect, and is outside this audit's blocking criteria.

## Summary

### Blocking (must fix)
- **[atlas-trades] `refundOrphanedStake` over-refunds by the amount a prior teardown already returned** (`services/atlas-trades/atlas.com/trades/trade/processor.go:1434-1459`, root cause interacting with `clearRefundedMesos` at `services/atlas-trades/atlas.com/trades/trade/settlement.go:1226-1234`). Any teardown (no restart required) that races an in-flight `AddMeso` re-stake, where the room already held a nonzero committed escrow total, mints `2×` that committed total in mesos once the stake's terminal status resolves. `TestUnwindZeroesARefundedMesoRowAndKeepsItsPendingStake` (`settlement_reconcile_test.go:500-535`) seeds the exact preconditions but never drives the stake to resolution, so the defect ships with green tests.

### Non-Blocking (should fix)
- `escrow/builder.go:44` — `ItemBuilder.Build()` performs no invariant validation (DOM-01). Pre-existing, not introduced by this diff.
- `escrow/administrator.go:24` (`toItemEntity`) is a free function in `administrator.go` rather than a `Model.ToEntity()` method in `entity.go` (FILE-04/DOM-02). Pre-existing placement, substantially rewritten by this diff without relocating.
- `trade/processor.go:1093-1113` (`returnOrphanedStage`, unchanged by this diff) has no compare-and-set guard against a genuine concurrent double-delivery of `StageSucceeded` for an orphaned row, which could double-grant an item in a narrower race than §1a's. Pre-existing, out of scope for these three commits, but shares the same class of defect as the meso finding above and should be looked at in the same pass.
