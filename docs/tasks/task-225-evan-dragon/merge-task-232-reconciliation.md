## Follow-up: ingress crash-loop from the route regeneration (c27aeeb91)

`72d114bac`'s route regeneration took the ingress down:

    [emerg] unknown "ns_atlas_families" variable

`deploy/k8s/base/atlas-ingress.yaml` holds the only place the `NS_*` nginx
variables are **defined** — a hand-maintained env block labelled "GENERATED by
tools/gen-routes.sh — do not edit by hand". `gen-routes.sh` never wrote to it;
it only emits `routes.conf.template.generated` and `ns-vars.generated.yaml`,
and nothing checked the two agreed. Regenerating moved dragons and families
onto their per-service `NS_*` variables, which the ingress did not define.
`NGINX_ENVSUBST_FILTER` substitutes only **defined** variables, so the
reference survived envsubst literally and nginx rejected the config — taking
down every route, not just those two.

Fixed by adding the two entries (set now 58/58) and by giving `gen-routes.sh` a
`check_ingress()` that fails when the ingress's `NS_*` set diverges from the
generated one, in both `--check` (so `tools/verify.sh`'s "routes drift" step
covers it) and post-write. Negative test confirms it fires.

**Lesson:** a generated routing table and a hand-maintained variable table are
two halves of one contract. Regenerating one without a check on the other is an
outage, not a drift.

## Observed, pre-existing, NOT touched

`kustomize build deploy/k8s/overlays/pr-sparse` renders **zero** `NS_*` env
definitions on its ingress (`grep -cE '^ *- name: NS_ATLAS_'` → 0), while `main`
and `pr` render 58. Verified identical on `origin/main` (0 vs 56), so this
predates task-225 and was not introduced here. It may be intentional — the
sparse overlay's `ns-overrides.yaml` anchor is filled by CI (task-232 Task 50) —
but if CI only injects *overrides* and not the base defaults, sparse-mode nginx
would hit the same `unknown variable` failure for every service. Worth a look by
someone who owns task-232; deliberately left alone here.
