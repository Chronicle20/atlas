## Findings

### 1. PASS — the new tests genuinely exercise the item-bearing branch

`libs/atlas-packet/parcel/clientbound/v83_test.go:222-260` (and the v72/v79
analogues) build `parcel.NewParcel(...).SetItem(item)` and assert the full
`Parcel.Encode` output byte-for-byte, including `wantEquipItemBytesVNN()`
appended after the `hasItem=0x01` byte. This exercises `parcel.go`'s
previously-dead `if p.item != nil { ... item.Encode(...) }` branch
(`libs/atlas-packet/parcel/parcel.go:157-173`), which every prior fixture
skipped by never attaching an item. Both arms named in the brief
(`PARCEL_ARRIVED`, `OPEN`) are covered in all three files.

### 2. PASS — expected bytes are hand-derived from the gate lines, not the encoder

Read `libs/atlas-packet/model/asset.go:226-286` (`encodeEquipableInfo`) and
`asset.go:495-511` (`encodeSlot`) directly and compared field-by-field against
each `wantEquipItemBytesVNN()` helper:

- `asset.go:507` — `MajorAtLeast(83)` gate: v83 writes `encodeSlot` as a
  2-byte short (`0x01, 0x00`); v72/v79 write it as 1 byte (`0x01`). Matches
  `v83_test.go:29` vs `v72_test.go:29`/`v79_test.go:29`.
- `asset.go:266` — `MajorAtLeast(79)` gate: v79/v83 write a 4-byte
  `hammersApplied` field (`v79_test.go:39`, `v83_test.go:41`); v72 omits it
  entirely (`v72_test.go:38`, with an explanatory comment, no phantom bytes).
- `MsTime(zero) == -1` confirmed at `libs/atlas-packet/model/ms_time.go:9-14`
  — the hand-built `0xff*8` literal in each helper is correct.
- Byte totals verified by hand: v72 = 77, v79 = 81 (+4 hammers), v83 = 82
  (+1 for the short slot vs v79's byte slot). Matches the report's table.

This is not derived from `item.Encode(...)` — the helper hand-assembles every
field per the brief's stated preference, satisfying "derive the expected item
bytes per version" and avoiding the self-referential-encoder trap the brief
warned about.
