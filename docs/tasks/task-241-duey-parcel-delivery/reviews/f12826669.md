## Priority 2 — the "single representative struct" claim

Confirmed **half (b)** of the report's finding and **corrected half (a)**.

**(b) Pre-existing, not introduced by this batch — CONFIRMED.** No grading

its sub-struct row reads `incomplete` for **every** version including
`gms_v95` (batch 7, already merged, with all four DUEY_ACTION arms
independently verified there), so that quirk is confirmed pre-existing too.

**(a) Mechanism — NOT accurate as stated.** I traced `Build`/
`worstCandidateCell`/`gradeOpCell`/`findReport` in
`tools/packet-audit/internal/matrix/build.go` and `grade.go` directly. The
op-row cell is **not** keyed to one hardcoded representative struct — it is
genuinely `worstCandidateCell` over **every** report whose `IDAName` shares
the op's base fname (`CParcelDlg::OnPacket`), because `parcel.yaml`'s
`PARCEL` entry has no `packet:` field, so `findReport`'s
disambiguation-by-packet-id never fires (`isPacketID("")` is false). All 7
of this batch's clientbound reports carry `IDAName:
"CParcelDlg::OnPacket#<Arm>"`, `baseFName` strips the `#` suffix, and every
one of them independently reports `Verdict: 0`/marker-found/`Verified` — so
worst-of-7 is `Verified`. The string `"parcel/clientbound/
ParcelAlarmGeneric"` the report points to is real, but it comes from
`rowPacketAndTier` (`build.go:426-439`), which is a **display-only**
label — the first writer alphabetically matching the op's fname in the
first version present — used for the `STATUS.md` "Packet" column, not for
grading. I confirmed this both by static trace and by the fact that
`gradeOpCell`'s tier1/marker/evidence computation for each candidate uses
that **candidate's own** `PacketID`, not the row-level representative.

The **practical conclusion still holds and is important**: because the 14
unmapped notice-only modes have no writer/report/marker at all, they are
simply invisible to the candidate pool rather than counted as failing
candidates — so `verified` here (7/21 claimable, no divergence found)
displays identically to a hypothetical 21/21-covered version. That is a
real, pre-existing blind spot in how the coverage matrix distinguishes
"fully proven" from "the claimable subset was proven, and the rest could
not be claimed without guessing," and it is worth carrying forward as a
known limitation of the tool (not something this batch should fix). The
14 unmapped modes are confirmed absent from `parcel.yaml`'s `operations`
table (no `jms_v185` key on any of SEND_ENABLE_ACTIONS, NOT_ENOUGH_MESOS,
INCORRECT_REQUEST, NAME_DOES_NOT_EXIST, SAME_ACCOUNT,
RECEIVER_STORAGE_FULL, RECEIVER_UNABLE_TO_RECEIVE, SENDER_UNIQUE_CONFLICT,
MESO_LIMIT, UNKNOWN_ERROR, RECV_ENABLE_ACTIONS, RECV_NO_FREE_SLOTS,
RECV_UNIQUE_CONFLICT, UNKNOWN_ERROR_2) and absent from
`libs/atlas-packet/parcel/clientbound/v185_test.go` (exactly 7 markers,
matching the 7 claimable keys) — the report's per-arm accounting is
accurate.

Non-blocking: the report's causal story ("keyed off a single
