# Kafka Topic Manifest — Before/After Migration

This records what the topic-manifest migration (task-276) actually changed,
derived from git evidence comparing `main-base` (`BASE`, the merge-base of
this branch with `main`) against `libs/atlas-kafka/gen/topics.yaml` at HEAD.
Every token name below is copied verbatim from the commands' output — none
is transcribed from `design.md`'s prose.

## 1. Counts

```
$ BASE=$(git merge-base HEAD main)
$ git show "$BASE:deploy/k8s/base/env-configmap.yaml" \
  | grep -oE '^  [A-Z0-9_]*TOPIC[A-Z0-9_]*:' | tr -d ' :' | sort > /tmp/topics-before.txt
$ grep -oE '^  - token: .*' libs/atlas-kafka/gen/topics.yaml | awk '{print $3}' | sort > /tmp/topics-after.txt
$ wc -l /tmp/topics-before.txt /tmp/topics-after.txt
 174 /tmp/topics-before.txt
 159 /tmp/topics-after.txt
 333 total
```

Before: 174 topic keys. After: 159 tokens declared in the manifest.
174 − 159 = 15 net fewer, which reconciles as **17 removed, 2 added**
(matching the design's predicted counts).

  - `EVENT_TOPIC_MONSTER_MOVEMENT` — `docs/tasks/task-212-monster-catch-items/audit.md`

  This corrects design §12's claim of "4 additionally"; live evidence found
  3, not 4. (A non-word-boundary grep for `EVENT_TOPIC_SKILL_MACRO` also hits
  many files, but every one of those is a substring match on the *new* token

are left in place, unused, per FR-6.2 — this migration deletes the
declaration, not the Kafka topic.

## 3. Added

```
$ comm -13 /tmp/topics-before.txt /tmp/topics-after.txt
STATUS_EVENT_TOPIC_SKILL_MACRO
STATUS_TOPIC_CASH_ITEM
```

Matches FR-6.1's expectation exactly.

For each, the rendered name change per environment: previously unsuffixed —
the deleted `gen-topic-config.sh`'s `^(COMMAND|EVENT)_TOPIC_` selector never
matched a `STATUS_` prefix, so no overlay ever suffixed them. Now, per the
manifest-driven overlays (`deploy/k8s/overlays/{main,pr,pr-sparse}/`), each
renders as:

- `<TOKEN>-main` on the `main` overlay
- `<TOKEN>-<env>` on the `pr` overlay
- `<TOKEN>-<baseline>` on the `pr-sparse` overlay

## 4. Consumer impact of the two renames

**`STATUS_TOPIC_CASH_ITEM`** has no consumer anywhere in the repo.

- Declaration: `services/atlas-cashshop/atlas.com/cashshop/kafka/message/item/kafka.go:7`
  (inside the `const (...)` block opened at line 5):
  ```go
  EnvStatusTopic  topic.Token = "STATUS_TOPIC_CASH_ITEM"
  ```
- Four producer sites, all in
  `services/atlas-cashshop/atlas.com/cashshop/cashshop/inventory/asset/processor.go`,
  lines 123, 180, 232, 318 — each a `mb.Put(item.EnvStatusTopic, ...)` call.
- `services/atlas-cashshop/atlas.com/cashshop/kafka/consumer/item/consumer.go`
  exists for this package but its `InitConsumers`/`InitHandlers` only wire
  `item.EnvCommandTopic` (`COMMAND_TOPIC_CASH_ITEM`); no `rf(` call anywhere
  in the repo registers `item.EnvStatusTopic`. Repointing it to a
  suffixed name loses nothing anyone reads.

**`STATUS_EVENT_TOPIC_SKILL_MACRO`** is consumed, by
`services/atlas-channel/atlas.com/channel/kafka/consumer/macro/consumer.go:29`:
```go
rf(consumer2.NewConfig(l)("skill_macro_status_event")(macro2.EnvStatusEventTopic)(consumerGroupId), consumer.SetHeaderParsers(...), consumer.SetStartOffset(kafka.LastOffset))
```
`consumer.SetStartOffset(kafka.LastOffset)` means this consumer never replays
history — it only reads messages produced after it starts consuming.
Repointing it at a freshly suffixed topic loses nothing it would have read.

## 5. In-flight outbox window

`libs/atlas-outbox` persists the **resolved** topic name, not the token,
into `outbox_entries.topic`:

- `entity.go:11` — `Topic string \`gorm:"column:topic;..."\`` on `Entity`.
- `bridge.go:42` — `EnqueueBuffer` resolves `token` to `t` via
  `topic.EnvProvider` (line 37) and writes `Enqueue(tx, Message{Topic: t, ...})`
  at line 42.

So any outbox row enqueued before this change ships still names the
old (unsuffixed) topic string, not the newly-suffixed rendered name.
`TopicWriterPool` sets `AllowAutoTopicCreation: true` (`publisher.go:86`),
so a writer for that old name is created on demand rather than erroring —
unsent rows drain rather than fail.

**Correction to the plan brief's framing:** the brief expected "neither
renamed token is produced through the outbox bridge today (cashshop's four
sites use `mb.Put` under the direct `message.Emit` path)." Tracing every
caller of the four `mb.Put(item.EnvStatusTopic, ...)` sites and the one
`mb.Put(macro2.EnvStatusEventTopic, ...)` site to their actual invocation
paths shows the opposite: all five run through the outbox bridge.

- All four `STATUS_TOPIC_CASH_ITEM` sites (`Create`, `CreateGift`,
  `CreateWithCashId`, `Expire`, called via `mb.Put(item.EnvStatusTopic, ...)`
  at lines 123, 180, 232, 318) are only ever invoked by their `*AndEmit`
  wrappers — `CreateAndEmit` (line 142), `CreateWithCashIdAndEmit` (line
  251), `ExpireAndEmit` (line 339, all in the same file), and `CreateGift`'s
  callers `GiftAndEmit`
  (`services/atlas-cashshop/atlas.com/cashshop/cashshop/processor_gift.go:54`)
  and `PurchaseRingAndEmit`
  (`services/atlas-cashshop/atlas.com/cashshop/cashshop/processor_ring.go:84`)
  — every one of which wraps `message.Emit(outbox.EmitProvider(p.l, p.ctx, tx))`,
  the outbox path, not the direct producer path.
- `STATUS_EVENT_TOPIC_SKILL_MACRO`'s one producer site
  (`services/atlas-skills/atlas.com/skills/macro/processor.go:117`,
  `mb.Put(macro2.EnvStatusEventTopic, ...)`) is only reached from `Update`,
  whose caller `UpdateAndEmit` (same file, line 129) also wraps
  `message.Emit(outbox.EmitProvider(p.l, p.ctx, tx))`.

So the window is real, not empty: an outbox row for either token, enqueued
before this branch deploys and still unsent when it does, carries the
pre-migration unsuffixed name. `AllowAutoTopicCreation: true` means it
drains to that old name rather than erroring — a topic gets auto-created
under the stale name and receives that one message, rather than the row
failing. This is the actual in-flight risk this migration carries for these
two tokens; it is recorded, not mitigated, per FR-6.3's requirement to
record it. Operationally the risk is small (both are low-volume status
events and the sweeper drains outbox rows quickly), but the window is real,
not "empty in practice" as the plan brief expected.

## 6. Behaviour change

`topic.EnvProvider` no longer falls back to the token itself when the
corresponding environment variable is unset — it now returns an error
(FR-1.5). Consumer registration paths (`InitConsumers`) fatal at boot on an
unresolved token; handler registration paths (`InitHandlers`) propagate the
error to their caller instead. This turns a silently-misdirected publish
(the old fallback quietly addressed a topic literally named after the Go
token, which nothing else would ever read) into a visible boot-time or
request-time failure — exactly the effect intended by removing the 17
orphans and renaming the two `STATUS_*` tokens: an unmanaged or unrenamed
token can no longer hide behind a fallback.
