## Skipped / Deferred Tasks

**Task 17 — PARTIAL.** The field-detail overview's `MapImagePanel` never receives runtime entities. `design.md`'s "FR-19 pins" correction (line 587) is explicit and unconditional for this task — unlike the tracked-object count (which the same design section and the plan both explicitly defer to Task 22), there is no stated dependency on `[278]` for live-monster pins: `useLiveMonsters` is already called in `FieldDetailPage.tsx` and its data (`monstersQuery.data`) is already used for `FieldSummaryPanels` and `FieldTabs`' monster count, but that same data is never passed to `MapImagePanel`. The plan's own Step 4 guidance ("Verify the prop names first... pass only props that component actually declares") anticipated a type-shape check: `MapImagePanel`'s `monsters` prop is typed `MapMonsterData[]` (definition shape: `template`, `mobTime`, `cy`, `f`, `rx0`, `rx1`, `hide`), while `LiveMonsterData`'s shape (`monsterId`, no `template`/`cy`/`f`) does not satisfy it directly — `MapImageOverlay`'s internal `computeMarkers` is generic and only needs `{id, attributes:{x,y}}`, so a small adapter (or a prop-type widening, in the spirit of the `9f6679907` fix commit) would have sufficed. No such adapter exists, and the omission is untested — `FieldDetailPage.test.tsx`'s 14 tests do not assert on `MapImagePanel`'s props. Impact: the field overview shows only the static map image with no illustrative monster pins, which is the entire visible content of FR-19 beyond the image itself.

## Known Issues Recorded (Not Plan-Adherence Gaps)

- `FieldMonstersTab.tsx:46` and `FieldObjectsTab.tsx:61` render their "no data" empty-state copy while the underlying query is still pending (fetch not yet resolved), because both treat `undefined` (loading) identically to a resolved empty array. Confirmed by direct code inspection. **This is a design omission, not a skipped plan task**: the plan's Task 19 and Task 20 test tables (and the shipped test files, which match those tables exactly — 9 and 8 tests respectively) do not include a `loading` test case for either component. Contrast Task 12, whose plan test table explicitly specified `| loading | <MapObjectsTable objects={undefined} /> | a skeleton/loading affordance renders, no crash |` and whose implementation (`MapObjectsTable.tsx:20-22`) correctly distinguishes `undefined` from `[]`. The plan simply never asked for the same treatment in `FieldMonstersTab`/`FieldObjectsTab`.
